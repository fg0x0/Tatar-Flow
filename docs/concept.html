01Асуудал

Дижитал банк = нэг вэб биш, 40+ микросервисийн нийлбэр. /api/transfer цаанаа limit-check, fee-calc, risk-engine, ledger рүү задарна. Burp үүнийг ойлгодоггүй — бүх мэдлэг тестерийн толгойд байдаг.

Функц харагдахгүй

Site map зөвхөн URL/method. “Энэ request яг ямар бизнес функц вэ” тодорхойгүй.

Утгын гарал үл мэдэгдэх

txnId, sessionRef хаанаас ирдэг вэ — өмнөх response-оос гараар ухаж, copy-paste хийнэ.

Төлөв/дараалал

init → OTP → confirm гэсэн олон алхмыг гараар барьж, алгасах/давхарлах тестийг санаж хийнэ.

Актор × объект

User A-гийн токеноор User B-ийн объектыг оролдох (BOLA/IDOR)-ыг зохион байгуулалтгүй, санамсаргүй хийдэг.

Үр дүнд нь: productCode=LOAN→SAVING, channel=MOBILE, amount=-100 гэж гараар сольж сольж — 3 өдөр.

02Шийдэл — нэг өгүүлбэрээр

Tatar Flow бол нийлмэл системийн API трафикийг бизнес функц + төлөв + актор + объект + хувьсагч гэсэн семантик загвар болгож, pentester-т контекстээр дүүргэгдсэн request, business-logic mutation-ууд, хамралтын хяналтыг нэг workspace-ээс өгдөг state-aware туршилтын орчин.

03Юу нь БИШ, юугаараа ялгарах вэ

Шударгаар: “API импортлоод request үүсгэх” нь аль хэдийн шийдэгдсэн (доор prior art). Tatar Flow-ийн шинэлэг тал өөр давхаргад байна.

Энэ БИШ (commodity)

OpenAPI/Postman импортлоод endpoint-ээс request үүсгэх. Үүнийг OpenAPI Parser, SpecOps, Burp API scan аль хэдийн хийдэг.

Харин ЭНЭ (шаантаг)

Трафикийг бизнес функцийн семантик загвар болгож, төлөв/актор/объектыг ойлгон, тестерт test context + coverage удирдуулах.

04Дата урсгал

05Семантик загвар — цөм

Endpoint жагсаалт биш. Аппликешнийг ийм давхаргаар загварчилна:

Application (Digital Bank)
 ├─ Services      Auth · Account · Payment · Loan …
 ├─ Functions     fund_transfer, create_beneficiary … (endpoint-тэй 1:1 биш)
 ├─ Endpoints     POST /transfer/init · /confirm · GET /status/{id}
 ├─ Actors        User A · User B · Operator · Admin
 ├─ Objects       Account · Beneficiary · Transfer
 ├─ Variables     token, account_id, txnId, otp  (гарал үүсэлтэй)
 ├─ States        INIT → PENDING → CONFIRMED → COMPLETED
 └─ Workflows     login → accounts → beneficiary → transfer → confirm

Функцийн бүртгэл (оператор өгнө)

# functions.yaml — банкны doc эсвэл reverse-ээс гаргаж ирсэн мэдлэг
- name: fund_transfer
  endpoints: ["POST /api/v1/transfer/init", "POST /api/v1/transfer/confirm"]
  reads:    [amount, fromAccount, toAccount, channelId]
  calls:    [limit-check, fee-calc, risk-engine]
  depends_on: [login, accounts_list, beneficiary_list]
  states:   [INIT, PENDING, CONFIRMED]
  produces: [txnId]
  logic:    "channelId=MOBILE ба amount>1M бол OTP шаардана"

Хувьсагчийн холбоос (context binding)

# өмнөх response-оос автоматаар авч дараагийн request-д оруулна
transfer/init  → response.transfer.id  ⇒  {{txnId}}
transfer/confirm  body: { "txnId": {{txnId}}, "otp": {{otp_token}} }
# хувьсагч юуг төлөөлж байгааг мэднэ:  account.owner=User A, transfer.dest=Beneficiary B

07Гаралтын жишээ

MVP-ийн 4 дэх алхам (baseline ↔ mutated diff) оператор дээр ингэж харагдана. Контекст сангаас {{txnId}}, {{otp_token}} автоматаар дүүрч, mutation зөвхөн НЭГ хувьсагчийг л сольж байгааг харуул:

# Tatar Flow — fund_transfer · baseline → mutation → diff

[baseline] # контекст сангаас дүүрсэн · actor: User A · state: PENDING
    POST /api/v1/transfer/confirm
    { "txnId": "TXN-88421",   ← {{txnId}}      transfer/init · response.transfer.id
      "otp":   "492013",      ← {{otp_token}}  OTP sms hook
      "productCode": "SAVING" }
    ⇒ 200 OK · 412 B · fee=1500 · state=CONFIRMED

[mutation: Actor swap] # User B-ийн токен, User A-гийн объект — бусад бүх зүйл ижил
    POST /api/v1/transfer/confirm
    { "txnId": "TXN-88421",   ← User A-гийн Transfer (солиогүй)
      "otp":   "492013",
      "productCode": "SAVING" }
    ⇒ 200 OK · 412 B · fee=1500 · state=CONFIRMED   # ← 403 БАЙХ ЁСТОЙ

[diff] baseline ↔ mutated
    status        200  →  200     ⚠ ялгаагүй
    body length   412  →  412     ⚠ ялгаагүй
    actor      User A  →  User B  ← цорын ганц өөрчлөлт
    объект     User A-гийн Transfer (хоёуланд ижил)

    ⇒ BOLA: өөр актор өөр хүний Transfer-ийг батлав. Объектын эрх шалгагдаагүй.
    coverage: fund_transfer/confirm · actor-swap ✓ · object-swap ✗ · step-skip ✗ · replay ✗

Хоёр хариулт бит-тэн адил байх нь дүгнэлтийн гол шалгуур: mutation НЭГ л хувьсагчийг сольсон бол ялгаагүй 200 гэдэг нь эрхийн шалгалт байхгүйг харуулна. Сүүлийн coverage мөр нь §04-ийн Coverage tracker — “fund_transfer дээр юу тестлэгдсэн, юу үлдсэн”.

08MVP — хамгийн өндөр ROI

  1. Burp history / HAR импортлох (mitmproxy эсвэл Burp extension).
  2. Request-ийг бизнес функцэд гараар/хагас-автоматаар оноох → functions.yaml.
  3. Response-оос хувьсагч гаргаж авах → контекст сан → дараагийн request-д авто inject.
  4. Baseline ↔ mutated request-ийг харьцуулах (diff) — §07-ийн гаралт.
  5. (Дараа нь) Ollama: request→функц ангилах, mutation санал болгох, ялгааг Монголоор тайлбарлах.

Эхний 4 нь ажиллачихвал өөрөө хэрэгтэй болно. Signing (HMAC/checksum) ба session-ийг эхэндээ гарын үсэггүй endpoint дээр орхиод дараа Relay-тэй холбож шийднэ.

10Экосистем ба анхааруулга

Tatar багана бүр “чамд X бэлэн байна → хаанаас эхлэх/юунд анхаарах вэ” гэсэн нэг хэв маягтай:

Triage  → Logs байна      → юу харах вэ
Kuber   → Findings байна   → юунд итгэх вэ
Path    → Paths байна      → алинаас эхлэх вэ
Flow    → Requests байна   → ямар функцийг ямар контекстээр тестлэх вэ
Relay   → Protocol         → хэрхэн харилцах вэ

Анхааруулга. Tatar Flow-г автомат exploit scanner болгож болохгүй. Үнэ цэнэ нь: ойлгох → загварчлах → төлөв зохион байгуулах → valid test context үүсгэх → coverage хянах → хүн баталгаажуулах. “100 payload авто-exploit” болговол ердийн scanner-ууд руу орж, өвөрмөц чанараа алдана. Тестлэх хүрээ нь зөвхөн бичгээр зөвшөөрөгдсөн engagement.
